## 2. Where this review sharpens the report's own framing

### 2.1 "Entropy decays gradually" undersells what the `ft06` curve actually shows

The report's Table 4.2 reports initial/final entropy (1.51 → 0.61) and calls the shape "healthy... decay gradually across the whole run." The image (`training_curves_hetero_stageA_ft06_seed0.png`, panel 3) shows something more specific: entropy drops fast for roughly the first 50,000–75,000 timesteps, then spends the remaining $\sim$325,000 timesteps (81% of the budget) oscillating in a band roughly 0.6–1.0 nats wide with **no further net decline** — the same interval the report's own §6.1 identifies as buying "very little" return improvement. These are the same phenomenon described twice in the report (once as an entropy observation, once as a return-plateau observation) without being explicitly connected. **Connecting them matters for the fix:** if entropy plateaus instead of continuing to decay, a fixed `ent_coef=0.01` is not just "holding entropy up on purpose" in a mild sense — it has established an entropy floor the policy cannot cross with this reward/loss balance, which is exactly what an entropy-coefficient schedule (report's own recommendation #3) is supposed to remove. This review treats §6.1's hypothesis (1) as **strengthened by the image**, not merely restated — see §4.

### 2.2 The mk01 "200× faster than GA" framing needs a footnote before it goes in the thesis

`week18_mk01.csv` gives GA a fixed 60-second time-limit budget (`time_limit_s`), not GA's convergence time — GA may have reached 42 well before 60 seconds elapsed, or may have needed the full budget; the CSV doesn't distinguish. The "$\sim$200×" ratio the report states (0.296s vs. 60.013s) is therefore a **budgeted-vs-actual** comparison, not a fair epoch-normalized latency comparison. This is not a mistake — `../../thesis/PreRegistration.md` §6 (H5) already anticipated exactly this problem and pre-registered the correct fix (median ms-per-decision-epoch, both methods, 5 timed replicates, ideally decoupled from GA's stopping criterion). **Recommendation: do not repeat the "200×" framing in the thesis body** — cite H5's eventual, properly-controlled measurement instead once it exists. Flagged here so it doesn't quietly become the number that gets cited in Chapter 6 before H5 is actually run.

### 2.3 The `ft06` win is real but is one instance, and should not be read as an H1 result

`../../thesis/PreRegistration.md` §2 froze H1's test set as all 43 bundled JSSP instances plus the FJSP-synthetic arm, evaluated with a paired Wilcoxon signed-rank test against the best PDR — specifically *to prevent* a strong single-instance result from being read as confirming the hypothesis. `ft06` beating every PDR and matching CP-SAT is an excellent, genuinely encouraging first data point, and the report does not claim otherwise — but this review states explicitly, for the record, what the report leaves implicit: **this is not evidence for or against H1 in the pre-registered sense.** One instance cannot produce a Wilcoxon $p$-value over $N=43$ pairs. The temptation this creates — to write up `ft06`'s result as if it already demonstrates static competitiveness — is exactly the HARKing risk `../../thesis/PreRegistration.md` exists to guard against, and is worth naming now, before Stage B/C produce more data and the temptation to cherry-pick the easiest instance's story gets stronger, not weaker.

### 2.4 One thing the report asserts without showing its derivation, now checked

The report's §6.2 hypothesis (2) claims the FJSP shaping potential $H$ is "a far looser relaxation... than under fixed routing" and implies (without stating outright) that this is not a bug in `fjsp_static_lower_bound` itself. This review read `envs/fjsp_env.py` directly to check: `fjsp_static_lower_bound` takes the **maximum of three independent relaxations** — a job bound (chain sequencing, cheapest eligible duration per operation), a forced-load bound (operations with only one eligible machine), and an average-load bound (total minimum work spread over all machines) — which is a legitimate, standard FJSP lower-bound construction, not a naive reuse of the JSSP formula. This rules out an alternative hypothesis the report doesn't explicitly consider and dismiss: that `static_lower_bound=36` is itself too loose and the real problem is a bad denominator, not a loose reward-shaping potential. **Confirmed: the gap is specifically between $H$ (the *reward-shaping* estimate, which relaxes machine contention entirely for a cheap per-step computation) and the tighter `static_lower_bound` (used only for RPD, not for the reward signal) — the report's hypothesis (2) is correctly diagnosed, not just plausibly diagnosed.**

This is why §4's action plan puts a small multi-seed check before, not after, any HPO spend.

## 4. Prioritized action plan for next week's sprint

Ordered by (evidence value gained) / (compute cost), not strictly by the report's own §8 list — merged with this review's additions from §2 and §3.

1. **Multi-seed sanity check on `ft06` first (new, this review's top priority).** 4 additional seeds (1–4) at the *existing* configuration, no code changes, ~2.5 hours total on this hardware (37 min × 4, `ft06` being the cheap instance). This is the cheapest possible way to know whether "greedy=55, matches CP-SAT" is a property of the policy or of seed 0 specifically, and it should gate how much confidence next week's other decisions get built on. **Do this before spending any budget on HPO** — an HPO search whose objective function is itself a single noisy seed's outcome is searching over noise as much as signal.
2. **Re-run `mk01` at 1,000,000 timesteps** (report §6.2 hypothesis 1, this review's rank 1) — the single highest-confidence, lowest-cost diagnostic available, $\approx$2.3h on this hardware. If the return curve plateaus within the extended budget and closes most of the remaining gap to `ft06`'s pattern, hypothesis 1 is confirmed as sufficient on its own and hypotheses 3/4 can be deprioritized. If it plateaus *without* closing the gap, that is direct evidence to promote hypothesis 3 or 4.
3. **Add an entropy-coefficient schedule** (linear or exponential decay, e.g. 0.01 → 0.001 over the training run) and re-run `ft06` — cheap, directly targets the plateau this review's §2.1 sharpened. This is also the natural first entry point for `HPO_TechSpec.md`'s search space, so this can be folded into step 5 rather than run as a separate one-off if the sprint's schedule is tight.
4. **Tighten the FJSP shaping potential** with a per-machine load floor (report §6.2 hypothesis 2) — only after step 2's result is in, since a tighter $H$ is a more invasive change (needs the reward-telescoping unit test re-applied, per the report's own discipline) and step 2 may already resolve most of the gap without it.
5. **Run the `HPO_TechSpec.md` search** (this document's companion) once steps 1–2 have produced a trustworthy, multi-seed-checked baseline to search around. Searching hyperparameters against a single untrusted seed's objective value risks tuning to that seed's noise rather than the policy's actual behavior — this is the direct link between this review's elevated concern in §3 rank 5 and the HPO spec's own design (see `HPO_TechSpec.md` §2 for how the objective function accounts for this).
6. **Widen `PerPairActorHead` to `hidden_dim=128`** only if steps 2 and 5 together do not close `mk01`'s gap — report's own conditional framing, preserved here since nothing this review found changes that condition.
7. **Reconcile `GNN_PPO_Architecture_Spec_v2.md` §0 and `TrainingPlan_Week17.md`** with the FJSP support that now exists (report §1.1c) — a documentation debt, not a training issue, but one that will compound if `AblationPlan.md`'s Month 7 runs are planned against a spec that still says FJSP is out of scope when the codebase has moved past that. Low cost, should not be deferred indefinitely.
8. **Run Stage B and Stage C** (`ft10`/`la16`–`la20` training, zero-shot generalization sweep) — the size-agnostic weight-transfer mechanism is already tested and ready (report §8 confirms `test_weight_transfer_across_instance_sizes` passes); this is the next scheduled step in `TrainingPlan_Week17.md`'s own curriculum and should follow, not precede, steps 1–2 so that Stage B trains from a baseline this review has already sanity-checked for seed sensitivity.

## 5. What `AblationPlan.md`'s Month 7 ablations should now specifically validate

Week 18 produced two pieces of evidence that sharpen what Axis 1 and Axis 2 of `AblationPlan.md` are actually testing — both ablations remain worth running, but the question each one answers is now more specific than it was when the plan was drafted.

### 5.1 Encoder axis (GIN vs. GAT-hybrid vs. homogeneous) — now has a load-bearing precondition to build on

`AblationPlan.md` §2.1 was drafted before any evidence existed that the eligibility relation actually does anything. Week 18 supplies that evidence directly: `test_eligibility_relation_actually_carries_signal` shows zeroing `adj_eligibility` provably changes the encoder's output, the machine-embedding norm is stable (7.8–9.4 across training, `ft06`; 7.81–7.85, `mk01`), and on `mk01` specifically the machine branch is described as "load-bearing" — half of every `(operation, machine)` logit. **This means the encoder ablation is no longer at risk of being a moot comparison** (if the relation had turned out to be a dead branch, homogeneous-vs-heterogeneous would have shown no difference for an uninteresting reason). It also **sharpens the GAT-hybrid variant's specific hypothesis**: given that hypothesis 3 (§3 above) attributes part of `mk01`'s gap to a *loose reward-shaping signal*, and attention lets a machine node weight its candidate operations unevenly rather than summing them uniformly, the GAT-hybrid run should be read as a test of whether **better machine-side aggregation can partially substitute for a looser $H$** — a more specific question than "is attention better than sum-aggregation in general," and one this sprint's `mk01` result motivates directly. Recommend running the encoder ablation on `mk01` (post-fix, i.e. after action-plan steps 2 and, if needed, 4) rather than only on the `ft06` + 10×10 JSSP tier `AblationPlan.md` originally specified — the JSSP tier is not where this sprint found an open problem for the encoder choice to help solve.

### 5.2 Reward-density axis (dense vs. sparse) — now has a concrete empirical bar to miss

`AblationPlan.md` §2.2 predicted, from the credit-assignment argument in Part B4, that sparse reward would show worse sample efficiency without necessarily worse final quality. Week 18's dense-reward run gives that prediction a concrete number to be compared against for the first time: dense reward crosses the best-PDR milestone (67 on `ft06`) at timestep 6,192 — **1.5% of the training budget**. The sparse-reward ablation's decision rule can now be stated concretely rather than only qualitatively: *does the sparse variant cross 67 at all within the same 400,000-timestep budget, and if so, at what fraction of it relative to dense's 1.5%?* A sparse run that needs, say, 30–50% of the budget to reach the same milestone dense reaches in 1.5% would be a strong, quotable confirmation of the credit-assignment argument already in the thesis's theoretical framework (Part B3.2/B4) — recommend stating this specific comparison as the ablation's headline metric in `AblationPlan.md`'s eventual write-up, rather than only the final-RPD comparison the plan currently emphasizes.

### 5.3 Disruption-aware reward axis (= H4) — unchanged, still blocked

Week 18 did not touch `DynamicJSSPEnv` wiring or the $\Delta_{\text{inest}}$ term (report §8 confirms both are still absent). No update to `../../thesis/PreRegistration.md` §5 or `AblationPlan.md` §2.3's blocked status is warranted by this sprint. Restated here only so the blocked status is not mistaken for "not yet checked."

### 5.4 Objective axis (single- vs. multi-objective) — the FJSP scope change is relevant

`AblationPlan.md` §2.4 was drafted assuming FJSP support was out of scope for the near term. It now exists (report §1.1c). This does not change the objective ablation's design, but it does mean the multi-objective weight grid could plausibly be evaluated on `mk01` in addition to the JSSP tier once action-plan step 7 (spec reconciliation) is done — noted here as a scope option for whoever plans Month 7 in detail, not a change this document is making unilaterally to a plan another document owns.
