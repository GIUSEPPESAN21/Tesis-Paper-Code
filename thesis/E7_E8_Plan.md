## 2. E7 — Disruption-aware reward comparison (κ ∈ {0, 0.5, 1.0})

### 2.1 Preconditions — what must be true before any new training run starts

E7 was pre-registered as blocked on two independent items (`PreRegistration.md` §0, §5): the `DynamicJSSPEnv` wiring, and the `κ·Δ_inest` reward term itself. **Only the first has cleared.** A direct read of `envs/dynamic_jssp_env.py::step()` (lines 279–318) confirms the reward computed today is still exactly `(previous_h − h_estimate) * reward_scale` — `info["planned_start_deviation"]` is computed and exposed (line 285, 313) but never subtracted from the reward. `../docs/planificacion/AblationPlan.md`'s own Ablation C table and `PreRegistration.md` §5 both say this plainly; this review confirms it is still accurate today, not stale. Four concrete preconditions follow, in priority order:

1. **Implement the `κ·Δ_inest` reward term**, gated by a `kappa` constructor parameter on `DynamicJSSPEnv` (default `0.0`, recovering the current dense reward exactly — this is what makes the κ=0 arm a true no-op, not an approximation). Use `planned_start_deviation` (already computed) as `Δ_inest`. **Scale-matching decision, not yet made anywhere in the docs reviewed:** `reward_scale` already normalizes the dense term for instance size; `planned_start_deviation` is currently raw simulation time units, unnormalized. Apply `reward_scale` to the `Δ_inest` term as well (`reward = (previous_h − h_estimate) * reward_scale − kappa * planned_start_deviation * reward_scale`), so that κ has a consistent, instance-size-independent meaning across `ft06` and `la01` — otherwise κ=0.5 could mean something very different in magnitude on the two instances, undermining the "0/0.5/1.0" comparison the pre-registration treats as a single ordinal factor. Add a unit test asserting κ=0 reproduces the current dense-reward trajectory bit-for-bit (extends the existing `test_default_config_matches_static_env_exactly` pattern).

2. **Fix or route around the GPU device-placement bug** (`../docs/logs/E0_CLOSEOUT_WEEK24.md`, root-caused: `build_hetero_maskable_ppo` builds via `MaskablePPO(...)` with `device="auto"`, and this machine's GPU driver reports a version mismatch that leaves `torch.cuda.is_available()` returning `True` while actually being unusable — SB3 ends up splitting the model across `cuda`/`cpu`). This is a **training-path** bug, and E7's two new training runs are the first thing all sprint that will actually exercise this exact helper. Recommended fix: pin `device="cpu"` explicitly in `build_hetero_maskable_ppo` when constructing on this machine (matches what `TrainedRLBaseline`'s evaluation path already does safely), rather than trusting `device="auto"` on a machine with a confirmed-broken driver report. **Verify with a fresh `pytest tests/test_hetero_policy.py` run (expect 3/3 currently-failing tests to pass) before committing any real GPU time to E7 training** — a mid-training crash or, worse, a silent cuda/cpu split producing a corrupted checkpoint, would be far more costly to discover after the fact than before.

3. **Build a training entrypoint against `DynamicJSSPEnv`.** None exists today — `experiments/train_hetero.py` (and `train_curriculum.py`) import and train only `JSSPEnv`/`FJSPEnv` (confirmed by direct read: line 66–69 imports, line 191/235 construction). This is new engineering, not a config flag: it needs (a) a `--dynamic` path that wraps `DynamicJSSPEnv` the same way `baselines/interface.py`'s new `_DynamicNodeFeatureAdapter` wraps it for evaluation (reuse that adapter's column-dropping logic so the training-time observation contract matches the frozen-checkpoint contract exactly — same `in_dim_ope=8`, `in_dim_mach=7` the encoder hard-requires), and (b) a decision on what disruption profile the policy trains under (§2.2 below, since this is not specified anywhere in the reviewed documents and materially affects what "κ=0.5" ends up meaning).

4. **Harden `run_evaluation.py`'s CSV-writing** (Finding #3): move from write-once-at-the-end to incremental (per-row or per-method) writes, or wrap the per-cell evaluation in catch-and-continue. E7's evaluation grid is comparable in size to E4–E6's RL arm (§2.4), and unlike that grid — which reused an already-debugged code path — E7 runs against **freshly trained, unvalidated checkpoints**. A late-run exception (e.g., a shape mismatch discovered only on the 400th of 540 rows) discarding the whole sweep is a materially higher risk here than it was in Week 24, precisely because the checkpoints are new. This is a half-day fix that removes a disproportionate amount of downside risk.

None of these four are optional if the two-sprint calendar is to be trusted; all four are estimated at well under a day each individually (see §3's schedule).

### 2.2 Training design decision — what disruption profile do the κ=0.5/1.0 policies train under?

This is not specified in `../docs/planificacion/Step 4 Thesis.md` D3, `PreRegistration.md` §5, or `../docs/planificacion/AblationPlan.md`'s Ablation C row — all three specify the reward formula and the *evaluation* grid (9 regimes), but not what the policy sees *during training*. Two options, with a recommendation:

- **Option A — single fixed regime during training** (e.g., always `A_k=0.90` breakdowns), then evaluate zero-shot across all 9 regimes. Cheapest, but conflates "did κ help" with "did the training regime match the eval regime," and risks the policy overfitting to one disruption axis.
- **Option B — domain-randomized/mixed training** (each episode samples one disruption axis and level uniformly from the same 9-regime grid E4–E6 evaluate on), then evaluate across all 9 regimes. More faithful to what H4's claim actually needs (a policy that is disruption-aware in general, not regime-specific), and consistent with how E3's own generalization framing already treats "trained on one distribution, evaluated more broadly" as the thesis's standard move.

**Recommendation: Option B.** It is not meaningfully more expensive (still 2 training runs, same total step budget) and it is the only version of the experiment that supports H4's decision rule as pre-registered — that rule asks for a majority (5/9) of regimes to show significant `ΔRI` improvement, which only makes interpretive sense if the training distribution wasn't already narrowed to a subset of those regimes. **This should be written down as an explicit, dated methodological note appended to `../docs/planificacion/AblationPlan.md` §2.3 before training starts** — not a pre-registration amendment (E7/H4 has no frozen instance-set or replicate-count commitment being changed, only an operational detail the original documents left open), but it belongs in writing given this document's own stated discipline about deciding things "before, not after" results exist.

### 2.3 A structural asymmetry to disclose, not hide: κ=0 is reused, κ>0 is freshly trained on the fixed contract

`PreRegistration.md` §5 is explicit that κ=0 is *the same trained policy already used for H1–H3*, reused rather than retrained — meaning the κ=0 arm is the policy trained against static `JSSPEnv` and rolled out via the adapter that this week's Finding #4 follow-up built, **carrying the quantified completion-gated/dispatch-gated legality mismatch** (a few percent of makespan on `ft06`/`la01` with disruptions off, ballooning to RI≈+1.7 under arrivals). The κ=0.5/1.0 policies, per §2.1's precondition #3, will be trained **directly** against the now-fixed `DynamicJSSPEnv` contract — meaning they will not inherit that specific mismatch (they learn completion-gated legality natively).

This means `ΔRI = RI_{κ>0} − RI_{κ=0}` is not a clean isolation of "does the reward term help" — some of any observed improvement could mechanically come from "trained on the correct contract at all," independent of κ. This is worth stating plainly for Chapter 6.4/7 regardless of which way the result comes out, and there is a cheap way to partially disentangle it: **if calendar time allows** (§3's contingency, not a hard requirement), a third, low-cost training run — κ=0 trained fresh against `DynamicJSSPEnv` (same domain-randomized regime as §2.2, same architecture, same step budget, just without the `Δ_inest` term) — would let the thesis report both `RI_{κ=0,\text{reused-adapter}}` and `RI_{κ=0,\text{retrained}}` as two rows, isolating the wiring-fix effect from the reward-shaping effect. This is **not** part of the frozen H4 decision rule and should not be presented as such; it is a supplementary robustness check on the *interpretation* of whatever H4 verdict comes out, offered here because the marginal training cost is small (§3) relative to what it buys in interpretability. If time is genuinely short, skip it and disclose the asymmetry as a stated limitation instead — both are honest options; silently ignoring the asymmetry is the only wrong one.

### 2.4 Grid, replication, and decision rule — kept as frozen

Per `PreRegistration.md` §5 (verbatim, unchanged by this review): instances `ft06`, `la01`; same 9 regimes as E4–E6 (`A_k∈{0.95,0.90,0.80}`, `σ∈{0.1,0.25,0.5}`, `ρ∈{0.7,0.85,0.95}`); **30 replicates/regime**; two quantities per κ∈{0.5,1.0}, each compared against κ=0: `ΔRI` (paired Wilcoxon by instance×seed) and `ΔRPD_nominal` (measured under `--disruption none`).

> **Accept H4** for a given κ iff: (a) Wilcoxon on `ΔRI` gives p<0.05 with median `ΔRI`<0 in ≥5/9 regimes, **and** (b) `ΔRPD_nominal` < 2 percentage points.
> (a) without (b) → report **"robustness gained at an unacceptable nominal cost."**
> (b) without (a) → report **"no measurable robustness benefit at this κ."**
> Neither → **Reject H4** for that κ.

**Replication count is not reduced.** `../docs/planificacion/FinalExperimentMatrix.md` §3 already established that raw compute is not the binding constraint anywhere in this matrix, and this week's E4–E6 run (a comparably-sized 9-regime×30-seed×2-instance grid) executed in a few hours once unblocked. The two new training runs are estimated at ~10–11 min/seed at `ft06` scale per the ablation study's own precedent (§2.7 of the matrix), "somewhat more" for `la01`-scale/dynamic-env overhead — still well under an hour of GPU compute each, **assuming §2.1 precondition #2 (device bug) is resolved**; if training falls back to CPU-only because the driver issue isn't fixed in time, this estimate does not hold and should be re-measured empirically on the first training run before assuming the second will finish on schedule. If the sprint genuinely runs short, the fallback is **defer a κ value, not shrink N** — training only κ=0.5 and reporting κ=1.0 as carried forward to the next window is a defensible, honestly-reported partial result; running both κ values at N=15 instead of 30 would quietly weaken the exact statistical power the pre-registration was written to protect, for no real time savings (§3's schedule shows the grid itself is not the expensive part).

## 4. E8 — Decision latency benchmarking across instance sizes

### 4.1 Why the completed Week 24 pass is not yet fit for H5's confirmatory claim

`PreRegistration.md` §6 requires, for **every** instance across the full E1 size range (`ft06` through `la31`–`la35`, 36–300 ops), `median(ms/decision_RL) < 1% × median(ms/decision_CP-SAT)`. `StatsAnalysis_TechSpec.md` §2.4 designed this to be computed directly from **E1's own `wall_clock_s` column** — E1 and E8 deliberately share one execution pass (matrix §2.8) — not from a separate E8 dataset. But `../docs/logs/EXPERIMENT_LOG_WEEK24.md`'s own E8 section reports that this exact column was captured "while E2 Arm A/B and E4–E6 were running concurrently in separate background processes on the same 16-core machine, competing for CPU — hence its large variance (σ up to 8× the mean...)," and even flags its own "dedicated pass" columns (run with "far less concurrent load," not *zero*) as the more-trustworthy-but-still-imperfect fallback. A confirmatory hypothesis test run on data the source document itself already calls noisy is not something a committee should be asked to accept at face value, and re-measuring is cheap (§3's Monday-morning slot).

### 4.2 Scope for the clean re-measurement

- **Full 43-instance coverage**, not just the 4-instance subset (`ft06`, `la05`, `la20`, `la35`) Week 24's "dedicated pass" used — H5's decision rule requires *every* instance in the size range to pass, and the matrix's own instance set for E8 is explicitly "same 43 instances as E1." The 4-instance subset was a reasonable exploratory choice for the multi-thread-vs-single-thread contrast (§4.3), not a substitute for full coverage.
- **Same protocol as E1** (1 deterministic + 4 stochastic seeds/instance, CP-SAT once), run on an **otherwise-idle machine** — schedule it before any other compute starts that day (§3, Monday AM), since E7's own training runs later in the week could just as easily contaminate a same-week timing pass if sequenced carelessly.
- **Replication count unchanged (5/instance)** — this already matches `PreRegistration.md` §6's own convention. The problem Week 24 surfaced is data quality (environmental noise), not sample size; adding more replicates on a contaminated machine would not fix that, only average over more noisy samples.
- **Retain the multi-thread/single-thread contrast** on the 4-instance subset as supplementary context (already collected and already correctly interpreted in the log — the `ft06` thread-overhead inversion is a known, explainable PyTorch effect, not an anomaly) — no need to redo unless the clean full pass reveals something inconsistent with it.

### 4.3 A framing correction worth a dated pre-registration amendment

`PreRegistration.md` §6 asks for timing "on the same hardware used for training... CPU-only inference timing should also be recorded separately if training used GPU" — a GPU-primary/CPU-secondary framing. Finding #1 (confirmed by direct code read, §2.1 above) establishes that **this codebase's actual evaluation path is CPU-only regardless of GPU availability** — `TrainedRLBaseline._policy_for` never calls `.to(device)`, so there is no GPU-inference number to report as "primary" even after the device-placement bug (§2.1) is fixed, because that bug is specific to the *training* helper (`build_hetero_maskable_ppo`/`MaskablePPO`), not the *evaluation* path (`baselines.interface`'s raw policy construction, which already pins CPU deliberately and correctly). Given the network is small enough that GPU inference would very plausibly not even be faster here — CP-SAT's own solve times already dwarf either — **recommend not building a GPU-inference evaluation path solely to satisfy D7's literal wording**, and instead log a short dated addendum to `PreRegistration.md` §7 (matching Amendment 1's style) stating: the evaluation architecture is CPU-only by implementation, "training hardware" and "CPU-only" collapse to one measurement in this codebase, and the multi-thread/single-thread contrast (already captured) is the closest honest analogue to D7's original "does the picture change under different hardware" intent. This keeps the amendment record honest and complete rather than silently reinterpreting §6 without a note, which is exactly the kind of undisclosed decision-rule drift the freeze protocol exists to prevent.

### 4.4 Decision rule — kept as frozen

> **Accept H5** iff, for every instance in the 43-instance range, median(ms/decision_RL) < 1% × median(ms/decision_CP-SAT). Also report whether the ratio widens with instance size (the figure Chapter 6.5 should lead with). **Reject H5** if the 1% threshold is violated for any instance.

Based on Week 24's already-collected numbers (RL: 1–5ms/decision; CP-SAT: 6–177ms total solve, i.e., considerably more per-decision once divided by `num_operations`), H5 is very likely to pass comfortably once cleanly re-measured — but the clean pass is still required before that verdict is written into Chapter 6, not skipped because the expected outcome seems obvious.
